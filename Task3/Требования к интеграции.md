# Требования к интеграции с партнёром "Умный дом"

## 1. Модель взаимодействия и зоны ответственности

1) PropDevelopment участвует в передаче биометрических данных и номеров автомобилей исключительно в рамках пользовательского ввода и не осуществляет их долговременное хранение.
Биометрические данные (изображения лиц) обрабатываются PropDevelopment только транзитно (in-memory) и не сохраняются в базах данных, логах или файловых хранилищах.
Хранение и обработка биометрических шаблонов осуществляется исключительно на стороне партнёра.

2) Номера автомобилей передаются партнёру для настройки доступа. Их хранение в системах PropDevelopment допускается только при наличии бизнес-обоснования и должно осуществляться в зашифрованном виде с ограниченным сроком хранения.
<mark>(Лучше вообще их не хранить, а хранить только какой-то id, по которому можно получить обратно номер через интеграцию, но это может повлиять на задержку при отображении в приложении. Если это критично, то хранить приемлимо.)</mark>

3) PropDevelopment взаимодействует с партнёром только через smart-home-integration-service


## 2. Требования к авторизации и контролю доступа

1) API партнёра обеспечивает проверку прав доступа на уровне каждого объекта (anti-BOLA): 
доступ к устройствам/дверям/шлагбаумам/событиям возможен только для субъектов, имеющих права на соответствующий объект.
2) обеспечивается строгая tenant-изоляция: дом/ЖК/УК/клиент PropDevelopment не имеет доступа к ресурсам других домов/ЖК/УК/клиентов.
3) Все операции управления доступом (добавить/удалить пользователя, выдать доступ, отозвать доступ) требуют авторизации и логируются.


## 3. Аутентификация и авторизация (протоколы)

### 3.1 Server-to-server
1) Для взаимодействия smart-home-integration-service <-> партнёр используется OAuth 2.0 (Client Credentials).
2) Доступ ограничивается через scopes и audience (токен выдаётся только для нужного API/ресурса).
3) Срок жизни access token ограничен, поддерживается ротация/отзыв.
4) Всё взаимодействие осуществляется через Mutual TLS с использованием TLS 1.2+ (лучше TLS 1.3)

### 3.1 Client-to-server (если необходима авторизация из приложения)
1) для авторизации используется OAuth 2.1 (c PKCE)
2) Принимаются только токены, подписанные сильными алгоритмами (например, RS256/ES256); alg=none и слабые/неподходящие алгоритмы запрещены.
3) В токенах проверяются exp, iss, aud, scope/roles; просроченные токены не принимаются, токены с некорректным aud/iss отклоняются.

## 4. Webhook
1) Webhook-запросы партнёра должны также осуществлять по mTLS
2) Webhook-запросы партнёра должны иметь timestamp + nonce / eventId для защиты от повторной отправки
3) Должна поддерживаться корреляция запрос <-> ответ: каждый асинхронный результат содержит operationId/correlationId, выданный PropDevelopment (или согласованный идентификатор).
4) Партнёр обязан поддерживать retry-механику доставки webhook (с backoff), а PropDevelopment обязан корректно обрабатывать повторы.


## 5. Управление ошибками и надёжность интеграции
1) API партнёра должен возвращать стандартизированные ошибки:
    - HTTP-коды
    - error codes для автоматической обработки
    - человекочитаемый message для диагностики
2) Для долгих операций партнёр поддерживает асинхронную модель:
    - 202 Accepted + operationId
    - результат возвращается через webhook
3) Должны быть определены ограничения по нагрузке:
    - rate limits
    - рекомендации по работе в случае всплесков активности
    - поведение при превышении лимитов

## 6. Логирование, мониторинг, аудит
Партнёр и PropDevelopment ведут журналирование:
- всех успешных и неуспешных попыток авторизации
- всех операций управления доступом
- всех команд “открыть дверь/шлагбаум” и результатов выполнения
- всех событий устройств.

Настроены алерты:
- всплески 401/403/429
- множественные неудачные попытки
- аномальная частота команд открытия
- недоставка webhook/рост задержек


# 7. Требования к данным и приватности
Принцип минимизации: передаются только данные, необходимые для сценария:
 
- идентификаторы пользователя/квартиры/дома в виде внутренних ID, без передачи ПДн сверх необходимого.
- В аналитический контур PropDevelopment передаются только usage events без ПД/биометрии/номеров.

Требования к срокам хранения:
- срок хранения событий и аудита согласован,
- предусмотрено удаление/очистка по требованиям законодательства и политики ретенции.
